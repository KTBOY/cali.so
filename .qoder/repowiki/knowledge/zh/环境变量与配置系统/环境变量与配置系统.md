该站点采用基于 Zod 的运行时校验 + 集中式 env.mjs 单例的模式管理所有运行期配置，并通过 config/ 目录对业务域配置进行二次封装。

1. 核心机制：Zod 校验 + Proxy 拦截
- 统一入口 env.mjs 使用 zod 定义 server/client 两套 schema（server 仅服务端、client 含 NEXT_PUBLIC_ 前缀变量），在启动时通过 safeParse 校验并抛出结构化错误。
- 返回对象被 Proxy 包裹，客户端访问非 NEXT_PUBLIC_ 变量时直接抛错，避免密钥泄露。
- 支持 SKIP_ENV_VALIDATION 跳过校验（便于测试或本地快速启动）。

2. 环境变量来源与分层
- .env 存放开发用示例值（包含 Clerk、Neon、Sanity、Resend、Upstash Redis 等第三方凭据）。
- 部署平台（Vercel）环境变量覆盖 .env，生产环境通过平台注入真实值。
- 变量按用途分为三类：
  - 服务端专用：DATABASE_URL、RESEND_API_KEY、UPSTASH_REDIS_*、VERCEL_ENV、SITE_NOTIFICATION_EMAIL_TO 等。
  - 客户端暴露：NEXT_PUBLIC_SANITY_*、NEXT_PUBLIC_SITE_URL、NEXT_PUBLIC_SITE_EMAIL_FROM 等。
  - 可选开关：LINK_PREVIEW_API_BASE_URL、NEXT_PUBLIC_SITE_LINK_PREVIEW_ENABLED。

3. 业务配置封装层 (config/)
- config/email.ts：从 env 派生 emailConfig，根据 VERCEL_ENV 自动切换 baseUrl（production -> 线上域名，否则 localhost）。
- config/kv.ts：集中定义 Upstash KV Key 命名规范（如 post:views:${id}），避免散落的字符串常量。
- config/nav.ts：导航菜单项作为纯数据导出，供 Header/Footer 渲染。

4. 领域子模块自持配置
- sanity/env.ts：在 Sanity 客户端初始化处再次断言必要变量缺失情况，提供友好错误信息。
- lib/mail.ts、lib/redis.ts：将第三方 SDK 实例化逻辑集中在 lib 层，依赖 env 注入凭据。

5. 开发者约定
- 新增环境变量必须同时写入 env.mjs 的对应 schema（server 或 client），否则构建时会报错。
- 需要跨模块复用的业务常量（KV key、邮件地址、导航项等）放入 config/，不要散落各处。
- 第三方服务单例（Resend、Redis）放在 lib/，由 env 注入配置，禁止在路由中直接读取 process.env。
