本仓库采用轻量、分散的错误处理方式，未建立统一的错误类型或全局中间件层，主要依赖 Next.js App Router 内置机制与 API Route 中的 try/catch。

1. 运行时配置校验
- sanity/env.ts 通过 assertValue 在模块加载时检查必需环境变量，缺失则直接 throw new Error(...)，属于启动期断言式错误处理。

2. API Route 错误响应
- 各 /app/api/* route 普遍使用 try/catch 包裹业务逻辑，捕获后返回 NextResponse.json({ error }, { status: 400 })（如 guestbook、comments）或 NextResponse.error()（如 newsletter）。
- 鉴权失败直接返回 { error: 'Not authenticated' } + 401；限流失败返回 429 文本响应或 NextResponse.error()。
- 没有自定义错误类或统一错误码枚举，错误信息以字符串形式随 JSON 返回。

3. 路由级 404 处理
- 动态页面（博客文章、Newsletter）在数据不存在时调用 notFound() 触发根目录的 app/not-found.tsx 客户端组件，呈现带 Spline 动画的 404 页面。
- 根级 app/not-found.tsx 是唯一的 404 入口，无其他全局错误页。

4. 中间件错误处理
- middleware.ts 基于 Clerk 的 authMiddleware，在 beforeAuth 中根据 Edge Config 的黑名单 IP 返回 403 JSON 或重写到 /blocked 页面，未对异常做显式捕获。

5. 日志记录
- 仅 newsletter route 的 catch 块中使用 console.error('[Newsletter]', error) 打印错误，其余 API 未输出结构化日志。

开发者约定与建议：
- API Route 应统一返回 { error: string } 结构并设置明确 HTTP 状态码，避免裸 NextResponse.error()。
- 需要区分业务错误与系统错误时可引入自定义错误类，集中到单一 catch 块处理。
- 建议为所有 API 增加结构化日志（如包含请求 ID、用户标识），便于排查生产问题。
- 对于可恢复的业务异常（如限流、认证失败），优先返回语义化 JSON 而非抛出异常。
